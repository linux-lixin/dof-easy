# Durable recharge contract

Run the adjacent `run.sh` only through `scripts/dof/local_environment.py`, with its sealed private PID/network namespace and fresh output. It creates a new MySQL 5.6 on namespace loopback and uses no real host or game data. Stage the verified MySQL files under `mysql/`, Java runtime including resolved `conf/security/java.security` under `java/`, actual Maven test jars under `dependencies/`, current compiled production/test classes plus public `dof/` catalog resources under `classes/`, `deploy/database/seed.sql`, `services/admin/database/dof-admin.sql`, and these scripts.

The Java contract independently requires the matching database UUID, a unique disposable marker and absence of both game schemas. It creates synthetic accounts and the actual seed wallet definition/known boundary trigger, then tests the actual service and management journal. Cleanup rechecks the identity and marker and drops only schemas it created. No private native UI sample is substituted for or needed by this database contract.

The 14 tests cover preview, request reuse, identity/version binding, write interruption before and after balance update, loss of the commit response, failed rollback through the actual Hikari pool, concurrent duplicate requests, conflicting previews, targeted one-time compensation, insufficient balance, known native balance limits, unknown schema/trigger refusal and actual permission changes. A real limited database role must fail when trigger metadata is hidden, then succeed after exact escaped-schema trigger grants. An unknown wallet column tested through Hikari must release its table locks before the pooled connection is reused; another actual connection verifies it can still read. Both InnoDB and MyISAM are exercised. MyISAM interruption is explicitly unknown at either the old or expected new balance; an acknowledgment preserves current data without asserting whether the original credit executed.

The InnoDB path durably prepares first, reacquires table locks with autocommit disabled, and commits balance plus receipt together. It never starts a new transaction after taking locks, and rolls back before unlocking. If rollback fails, it closes the unwrapped physical driver connection instead of returning an uncommitted proxy to Hikari. Validation failures release table locks before returning a connection to the pool. See the [MySQL table-lock transaction rules](https://dev.mysql.com/doc/refman/8.4/en/lock-tables.html); the contract must additionally pass on the actual pinned MySQL 5.6 runtime used here. SQL/connection fault injection tests the implementation; it is not a power-loss, real server or original tool equivalence test.

Publish only `recharge-result.json` and namespace provenance. Keep logs, temporary database files and fixture properties private. This test does not prove native gateway/client receipt, actual deployment permissions, container rebuild or the remaining CDK/mail/exchange workflows.

The same runner additionally executes three `ManagedMailReceiptContractTest` cases against the actual seed `postal` and `letter` table definitions. A consumed/deleted postal row does not erase its receipt, and stale completion cannot overwrite it. Autocommit and non-PREPARED completion are rejected. These are synthetic recipient/text fixtures for the journal primitive, not native encoding, original-tool behavior, batch delivery or game receipt verification.

Twelve `ManagedPostalContractTest` cases exercise the actual sender: Chinese database text and linked letters, gold/text-only mail, receipt interruption, committed response loss, MyISAM uncertainty/acknowledgment, stale recipient/generation, wrong instance, item rules, schema/trigger refusal, concurrent duplicate submissions, PVF changes after native INSERT and failed rollback through Hikari. Item metadata and PVF fingerprint files in these cases are explicitly synthetic; they do not prove actual native PVF parsing or client display. Avatar, creature and creature-equipment flags remain unverified and are rejected instead of issuing them as ordinary gear. The HTTP read regression also checks that the old unversioned admin POST returns 400 before reaching the old DAO; internal CDK/task callers retain their separate service pending their own protocol work.
